# Task: Inventory the current rebuild.net site (Phase 1, Step 0c)

## Context
Read `AGENTS.md` and `PHASE_1_BRIEF.md` first. We are about to rebuild this Eleventy site as a SolidStart app. Before writing any new code, we need a precise inventory of what exists today — every page, component, script, data source, form, and route. This inventory becomes the rebuild checklist and the source of the redirect map (so no URLs break).

**Important — stale docs:** The repo contains old planning/reference docs (`SOLIDSTART_MIGRATION_PLAN.md`, `docs/archive/STACK_ARCHITECTURE.md`, `docs/archive/QUICK_REFERENCE.md`, `docs/archive/DESIGN_DECISIONS.md`, and any other `.md` files besides `README.md`). These are **outdated and will be removed** — they describe an earlier plan (static SolidStart on Vercel) that has been superseded. **Do not trust them as a source of truth.** Trust only the actual source files and `README.md`. If you spot contradictions between the old docs and the code, note them in the Discrepancies section but resolve in favour of what the code actually does.

## What to do

### 0. Pre-step: flag stale docs for removal
List every `.md` file in the repo root and `docs/` directory. Confirm which ones are stale planning docs that should be removed. The following should be **kept**: `README.md`, `AGENTS.md`, `CLAUDE.md`, `PHASE_1_BRIEF.md`, `REBUILD_PLATFORM_TRANSITION_PLAN.md`, `STATUS.md`. Everything else (e.g. `SOLIDSTART_MIGRATION_PLAN.md`, anything in `docs/archive/`) should be listed in your output under a "Stale docs to remove" heading so the maintainer can confirm and delete them.

### 1. Pages & routes
List every page the site generates. For each:
- Source file path (e.g. `src/pages/about.html`)
- Output URL (from the `permalink` frontmatter or Eleventy convention)
- Page title (from frontmatter or template)

Also list any generated collection pages (journal posts, insight posts) with their URL pattern.

### 2. Components (Nunjucks includes/macros)
List every file in `src/_includes/` recursively. For each:
- File path
- One-line description of what it renders
- Where it's used (which pages/layouts include it)

### 3. Layouts
List every layout in `src/_includes/layouts/`. Note the inheritance chain (which layout extends which).

### 4. Client-side scripts
List every JS file in `src/scripts/`. For each:
- File path
- Line count
- One-line description of what it does
- How it's loaded (inline, script tag in which template, deferred, etc.)

### 5. Data sources
List every file in `src/_data/`. For each:
- File path
- Type (JSON, JS with fetch, JS computed)
- What it provides (e.g. "Notion directory entries, filtered to Published only")
- Whether it has a cache/fallback mechanism

Also list the `insights/` and `journal/` markdown directories: how many files in each, what frontmatter fields they use (sample 2–3 files to confirm the field set).

### 6. Forms
List every form in `src/forms/`. For each:
- File path + form name (the `data-form="..."` trigger value)
- What fields it collects
- Where it submits (which backend: Bunny Edge Script, MailerLite, Notion — trace through `form-handler.js` and `edge-script.js`)

### 7. Static assets
Summarise what's in `src/public/` (don't list every image — just the categories: images, fonts, favicons, etc.) and note any assets referenced from Bunny CDN URLs in templates.

### 8. Build config & plugins
From `.eleventy.js` / `eleventy.config.js`:
- List all custom collections, filters, shortcodes, and plugins.
- Note the input/output dirs and any passthrough copies.

### 9. SEO artifacts
Confirm which of these exist and their exact output paths:
- `sitemap.xml` — generated by which plugin?
- RSS/Atom feed — at `/feed.xml` or `/rss.xml`? Generated how?
- `robots.txt` — is it a static file or generated?
- Social/OG meta tags — which template handles them?

### 10. Environment variables
**Do not rely on `.env.example` — it may be incomplete.** Instead, find every env var the project actually uses by searching the entire codebase:

```bash
# Find all references to process.env or import.meta.env
grep -rn "process\.env\." --include="*.js" --include="*.ts" --include="*.mjs" --include="*.cjs" .
grep -rn "import\.meta\.env\." --include="*.js" --include="*.ts" --include="*.html" .
```

Also check:
- `.env.example` (if it exists) for any vars listed there but not found in code (possibly dead).
- Any hardcoded API URLs or CDN paths in templates/scripts that imply a configured service (Bunny CDN URLs, MailerLite endpoints, Notion API calls, Pirsch snippet, etc.) — these often have companion env vars or are env vars that should be.
- The Eleventy config and data files (especially `builders.js` and `edge-script.js`) — these are the most likely places for undocumented vars.
- Vercel project settings are not accessible from the repo, so list any vars you find in code and flag any that seem to be used but have no `.env.example` entry as **"undocumented — confirm with maintainer."**

For each var found, note:
- Variable name
- Where it's referenced (file + line)
- What it's for (inferred from context)
- Build-time or runtime
- Whether it appears in `.env.example` ("documented" / "undocumented")
